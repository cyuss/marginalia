# Hardware spike — resolving U11 (display access) read-only

Status: **ready to run — not yet executed**
Resolves: **U11** (blocking), and opportunistically U12, U14, U16, plus the
first real resource-budget numbers.
Feeds: [ADR-002](../adr/ADR-002-remarkable-ui-and-runtime.md)

---

## 1. What this decides

[ADR-002](../adr/ADR-002-remarkable-ui-and-runtime.md) is deliberately open
because I will not resolve an unknown by guessing, and I will not resolve it by
picking the more invasive option. This spike gathers the evidence that closes
it.

The question it answers: **can a process that is not the native reading
application obtain display access on this device and firmware, and if so, by
what mechanism?**

The answer determines whether the product has an on-device interface (options
A/B/C) or whether the native reader becomes the interface (option D).

## 2. Before you start — consent and reversibility

This spike requires **developer access**, which you enable yourself on the
device (Settings → Help → About → copyright/licence area exposes an SSH
password on reMarkable firmware; the exact path varies by version).

Things worth knowing, and worth verifying yourself rather than taking from me:

- enabling developer access is a setting you control and can turn off again;
- the SSH password is generated by the device, not chosen by you, and it can
  change after a firmware update;
- **nothing in this spike writes to the device.** Every command reads. Every
  output is redirected to a file on *your computer*, never onto the device.

If you are not comfortable enabling developer access, say so — option D in
ADR-002 is designed to need none of this, and we would instead spike its
interaction mechanism, which is pure desktop work.

## 3. Absolute rules for this session

```
✗ no writes of any kind to the device filesystem
✗ no `systemctl stop`, `start`, `restart`, `enable`, or `disable`
✗ no package installation, no opkg, no Toltec, no curl | sh
✗ no LD_PRELOAD, no launching anything
✗ no editing any file, including in your own home directory on the device
✗ no `sudo`-style privilege changes, no chmod, no chown
✓ read, list, and report only
```

If a command in this document appears to modify something, **do not run it and
tell me** — it is a mistake in this document, not an instruction to follow.

## 4. Setup

Connect the device by USB. The USB network interface is normally reachable at
`10.11.99.1`. Create a directory on **your computer** for the evidence:

```bash
mkdir -p docs/remarkable/validation/raw && cd docs/remarkable/validation/raw
```

Define a helper so every probe is captured identically:

```bash
probe() { echo "### $1"; ssh root@10.11.99.1 "$1" 2>&1; echo; }
```

Every section below writes one file. Nothing lands on the device.

## 5. Probe A — identity and firmware

```bash
{ probe 'cat /etc/version'
  probe 'cat /etc/os-release'
  probe 'uname -a'
  probe 'cat /proc/device-tree/model'
  probe 'cat /proc/cpuinfo'
} > probe-a-identity.txt
```

**Feeds:** the `firmware` and `model` fields of every
`packages/remarkable/compatibility/matrix.toml` entry, and confirms that
`armv7-unknown-linux-gnueabihf` is the right target (currently an inference
from the SoC family, verified only by the fact that it compiles).

## 6. Probe B — the display question (the core of U11)

```bash
{ probe 'ls -la /dev/fb* 2>&1'
  probe 'ls -la /sys/class/graphics/ 2>&1'
  probe 'cat /sys/class/graphics/fb0/name 2>&1'
  probe 'cat /sys/class/graphics/fb0/virtual_size 2>&1'
  probe 'cat /sys/class/graphics/fb0/bits_per_pixel 2>&1'
  probe 'ls /dev/input/ 2>&1'
  probe 'cat /proc/bus/input/devices 2>&1'
  probe 'ls -la /dev/mxs_dcp /dev/epdc* 2>&1'
  probe 'ps aux 2>&1 | head -40'
  probe 'ldd $(command -v xochitl) 2>&1'
  probe 'cat /proc/$(pidof xochitl)/maps 2>&1 | head -60'
} > probe-b-display.txt
```

Reading `ldd` output and a process map is inspection, not injection. It tells
us which graphics stack the reading application actually uses, which is exactly
what we need to know and currently do not.

### How to read the result

| Observation | What it means for ADR-002 |
|---|---|
| A usable framebuffer device exists, with plausible geometry, and is not exclusively held | Option B becomes worth costing. Still needs the `xochitl`-stopped question answered. |
| No framebuffer device, or it exists but does not correspond to the panel | Options A/B are likely dead without a shim. **Option D becomes the leading candidate.** |
| The reading application links a display stack we cannot use without loading into its process | Option A is confirmed to require injection → **invariant 1 violation, so it is off the table unless you relax the invariant explicitly.** |

I am not going to predict which of these you will see. That is the entire point
of running the probe.

## 7. Probe C — storage, for U12

```bash
{ probe 'df -h'
  probe 'mount'
  probe 'cat /proc/mounts'
  probe 'stat -f /home/root'
  probe 'ls -la /home/root/'
} > probe-c-storage.txt
```

**Feeds:** whether SQLite WAL is safe here (WAL needs shared-memory support
from the filesystem), and where a manifest-owned application directory could
live. `/home/root` is the conventional location that survives firmware updates
— **verify, do not assume**, and record the evidence either way (U13).

## 8. Probe D — network and TLS, for U16

```bash
{ probe 'ls /etc/ssl/certs/ 2>&1 | head -20'
  probe 'ls -la /etc/ssl/certs/ca-certificates.crt 2>&1'
  probe 'command -v curl openssl wget 2>&1'
  probe 'curl -sS -o /dev/null -w "%{http_code} %{ssl_verify_result}\n" https://api.zotero.org/ 2>&1'
} > probe-d-network.txt
```

The last command performs an unauthenticated HTTPS request to a public
endpoint and discards the body. It writes nothing and sends no credentials. It
answers the one question that matters for Phase 2: **can this device complete a
TLS handshake to the Zotero API using a root store it already has**, or must we
bundle one?

## 9. Probe E — resource baseline, for the budgets

```bash
{ probe 'free -m'
  probe 'cat /proc/meminfo | head -10'
  probe 'uptime'
  probe 'cat /proc/loadavg'
  probe 'cat /sys/class/power_supply/*/capacity 2>&1'
  probe 'ps aux --sort=-rss 2>&1 | head -15'
} > probe-e-resources.txt
```

**Feeds:** the roadmap's required budget envelope. These are *idle system*
numbers, i.e. the headroom we have to fit inside — not our own consumption,
which cannot be measured until something of ours runs.

## 10. What to send back

The five `probe-*.txt` files. Before sending, skim them for anything you would
rather not share — a device serial appears in some outputs, and the codebase
deliberately stores only a hash of it. Redact freely; the technical answers do
not depend on the serial.

## 11. What happens next

1. I read the evidence and write it into
   `docs/remarkable/validation/<firmware>.md`.
2. Matrix entries move off `UNKNOWN` **only** for capabilities the probes
   actually demonstrated, each with a `tested_at` date — the loader forces
   `UNKNOWN` on any entry without one, so an optimistic edit cannot grant
   permissions.
3. ADR-002 gets a decision, or a costed shortlist if the evidence is
   ambiguous.
4. U12, U16 and the budget baseline are updated from probes C, D and E.
5. Phase 1 unblocks, in whichever shape the evidence supports.

If the evidence says option D, that is a good outcome, not a defeat: it is the
only shape that satisfies all fourteen invariants, and it reuses the part of
the device that is genuinely excellent instead of competing with it.

## 12. Explicitly not in this spike

Writing a test file. Stopping any service. Installing anything. Loading any
library into any process. Rendering anything to the screen. Touching a user
document. Any of these would move this from a read-only inspection to a device
modification, and none of them is needed to answer the question.
