# Marginalia — Domain Model

Status: **Draft v1 — awaiting validation**

The domain lives in `packages/core` and depends on nothing. Rust is the source
of truth; TypeScript types are generated (`ts-rs`) into `packages/shared-types`.

---

## 1. Identity rules

1. **A filename is never an identity.** Filenames change, collide, and are
   rewritten by `xochitl`.
2. Every cross-system link goes through `DocumentMapping`.
3. Every entity has a stable ULID `id` generated by Marginalia, independent of
   Zotero keys and device UUIDs.
4. Content identity uses SHA-256 checksums, stored per role (`original`,
   `working`, `derived`, `on_device`).

## 2. Entity map


## 3. Bibliographic entities (Zotero-owned, mirrored read-mostly)

### ZoteroItem
```
id                 ULID
zotero_key         TEXT   unique, Zotero item key
zotero_version     INT    for incremental sync
library_id         TEXT
item_type          TEXT   journalArticle | book | report | ...
title              TEXT
creators           JSON   [{creator_type, first, last}]
publication        TEXT?
year               INT?
doi                TEXT?
isbn               TEXT?
url                TEXT?
abstract           TEXT?
date_added         TS
date_modified      TS
raw                JSON   full Zotero payload, for forward compatibility
deleted_remote     BOOL
```
`raw` is retained so a Zotero schema addition never loses data before we model it.

### ZoteroAttachment
```
id                 ULID
zotero_item_id     → ZoteroItem
zotero_key         TEXT unique
link_mode          imported_file | imported_url | linked_file | linked_url
content_type       TEXT   (application/pdf, ...)
filename           TEXT
local_path         TEXT?  resolved path on this machine, may be null
file_size_bytes    INT?
availability       AttachmentAvailability
checksum_sha256    TEXT?
```

```
AttachmentAvailability =
    UNKNOWN            not yet resolved
  | NOT_PRESENT        Zotero knows of it, file not on this machine
  | AVAILABLE_LOCAL    file resolved and readable
  | UNREADABLE         path exists but invalid/corrupt/permission denied
```

> **INV-2 note.** `AVAILABLE_LOCAL` means "we could send this if asked". It is
> displayed as *PDF available*. It never triggers a transfer.

### ZoteroCollection
```
id, zotero_key, zotero_version, name, parent_collection_id?, library_id
```

## 4. Marginalia document entities

### Document
The Marginalia-side notion of "a readable thing we track".
```
id                 ULID
title              TEXT     display title (from Zotero when linked)
source             ZOTERO | LOCAL_FILE | DEVICE_ONLY
page_count         INT?
state              DocumentState        (see DOCUMENT_STATE_MACHINE.md)
created_at, updated_at
```

### DocumentMapping
The critical join. One row per (Zotero attachment ↔ device document) pairing.
```
id                     ULID
zotero_item_key        TEXT?
zotero_attachment_key  TEXT?
local_document_id      → Document
remarkable_document_id TEXT?    device UUID as reported by the device
original_filename      TEXT
original_checksum      TEXT     SHA-256 of the immutable Zotero source
working_checksum       TEXT?    SHA-256 of our working copy
device_checksum        TEXT?    SHA-256 verified after transfer
device_state           DocumentState
transferred_at         TS?
created_at, updated_at, last_synced_at
```
Rules:
- `original_checksum` is written once and never updated. If the Zotero source
  file changes, that is a *new* mapping generation, surfaced as a conflict.
- `remarkable_document_id` is authoritative for device identity. A device
  document whose UUID we don't know is *not ours* and is never touched.

### ReadingState
```
id, document_id, device_id?
current_page, total_pages, progress_percent
last_opened_at?, last_annotation_at?
status = UNREAD | READING | COMPLETED | ARCHIVED
```
Filtering and workflow only. No streaks, no badges, no gamification.

## 5. Annotation entities

All three annotation kinds share a `provenance` block, because an annotation
without provenance is unusable for research:

```
Provenance {
  document_id
  page_number         1-based, as printed in the PDF page index
  source              REMARKABLE | DESKTOP | ZOTERO | IMPORTED
  source_ref          TEXT?   device page uuid / .rm layer id / zotero key
  extraction_version  INT     which extractor version produced this
  confidence          FLOAT?  for text-mapped highlights
}
```

### Highlight
```
id
document_id, page_number
bounding_boxes     JSON [{x, y, w, h}]  PDF user space, origin bottom-left
selected_text      TEXT?      null when text mapping failed
context_before     TEXT?
context_after      TEXT?
color              TEXT?
type               HighlightType
source             AnnotationSource
zotero_annotation_key TEXT?
created_at, modified_at
+ provenance
```

```
HighlightType = PLAIN | IMPORTANT | CITATION | QUESTION | IDEA | REFERENCE
```
Default is `PLAIN`. **Types are never inferred automatically.** They are set by
the user, or by an explicit user-configured mapping (e.g. "yellow → CITATION").

### SideNote
Page/anchor-scoped structured prose.
```
id, document_id, page_number
anchor_x, anchor_y        nullable — a note may be page-level
highlight_id?             optional link to the highlight it comments on
content, content_type = PLAIN | MARKDOWN
zotero_note_key?
created_at, modified_at
+ provenance
```

### StickyNote
Point-anchored note with a visual footprint.
```
id, document_id, page_number
x, y, anchor_width, anchor_height
content
zotero_annotation_key?
created_at, modified_at
+ provenance
```

### Annotation (read model, not a table)
The Annotation Inbox and Search operate on a unified projection over
`Highlight ∪ SideNote ∪ StickyNote`, exposing: `kind, document, page, text,
created_at, type, tags, provenance`. Implemented as a SQL view + FTS index, so
adding a fourth kind later does not fork the UI.

## 6. Tagging

reMarkable has native tags. Zotero has tags. Marginalia **bridges**, it does not
own a third tag system.

### Tag
```
id, namespace = ZOTERO | REMARKABLE | MARGINALIA, name, normalized_name
```

### TagMapping
```
id
zotero_tag          TEXT
remarkable_tag      TEXT
direction           ZOTERO_TO_RM | RM_TO_ZOTERO | BIDIRECTIONAL
confirmed_by_user   BOOL     mappings are NEVER auto-applied unconfirmed
created_at, updated_at
```
Case/spacing differences (`machine-learning` vs `Machine Learning`) produce a
*suggestion*, surfaced for confirmation. Never a silent rename, never a
destructive merge.

## 7. Device entities

### Device
```
id, kind = RM2 (RM1/RMPP reserved), serial_hash, display_name
firmware_version TEXT, firmware_known BOOL
connection = USB | WIFI | UNKNOWN
last_seen_at, storage_total_bytes?, storage_free_bytes?
safe_mode BOOL (default true)
```
`serial_hash` — we store a hash, not the serial.

### DeviceCapability
```
id, device_id, capability CapabilityKey, status CapabilityStatus,
source = MATRIX | PROBED | USER_OVERRIDE, tested_at?, notes?
```
See [`DEVICE_CAPABILITY_MODEL.md`](./DEVICE_CAPABILITY_MODEL.md).

### SafetySnapshot
```
id, device_id, created_at, operation, affected_documents JSON,
checksums JSON, storage_before JSON,
status = PENDING | VERIFIED | FAILED | CONSUMED | RESTORED
```
A snapshot that cannot be *verified* is treated as absent → operation denied.

## 8. Sync entities

### SyncJob
```
id, kind = ZOTERO_METADATA | DEVICE_SCAN | ANNOTATION_INGEST
        | TRANSFER | ZOTERO_EXPORT | TAG_BRIDGE
state SyncJobState, started_at, finished_at?
counters JSON, error? JSON, triggered_by = USER | SCHEDULE | STARTUP
```
`TRANSFER` jobs can only be created by an explicit user intent token.

### SyncOperation
One atomic unit inside a job; the journal is built from these.
```
id, sync_job_id, seq, kind, target_ref, state, detail JSON,
idempotency_key TEXT unique, attempted_at, completed_at?
```
`idempotency_key` makes a duplicate `Send` a no-op rather than a second copy.

## 9. Invariants enforced in the domain layer

| # | Invariant | Enforcement |
|---|---|---|
| D1 | A `SyncJob(ZOTERO_METADATA)` contains zero `TRANSFER` operations | type-level: separate operation enums |
| D2 | `original_checksum` is immutable after first write | DB trigger + repository guard |
| D3 | Every annotation has complete provenance | non-nullable columns |
| D4 | No device write without a `WriteGrant` | function signatures |
| D5 | `TagMapping` unconfirmed ⇒ never applied | executor precondition |
| D6 | A `Document` in `METADATA_ONLY` has no device id | state machine |
| D7 | Deleting a device document is user-initiated only | no automatic delete API exists |
